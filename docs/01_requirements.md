## 1. プロジェクト概要

### 1.1 目的

X（旧 Twitter）でのアフィリエイト収益化を目指す個人・法人向けに、予約投稿・リンク管理・分析・自動化を一元化する SaaS 型 Web アプリケーションを提供する。垢 BAN リスクを最小限に抑えながら運用効率を最大化することを最優先とする。

### 1.2 提供形態

| 項目 | 内容 |
|------|------|
| 形態 | 月額課金制 Web アプリケーション |
| 対応環境 | Windows 11 / Chrome・Edge 最新版 |
| 提供方式 | SaaS（マルチテナント） |
| X 連携方式 | Twikit（Python ライブラリ） |

### 1.3 プラン体系

| プラン | 月額 | 管理アカウント数 | 予約投稿数/月 | 自動タスク |
|--------|------|-----------------|--------------|------------|
| Starter | ¥2,980 | 1 | 100 | 無効 |
| Pro | ¥7,980 | 5 | 1,000 | 有効 |
| Business | ¥19,800 | 20 | 無制限 | 有効 |

#### 投稿実行フロー

```
[スケジューラー（Celery Beat）]
  └─ 予約時刻到達
      └─ Celery Worker がキューから取得
          └─ Twikit クライアントで投稿実行
              ├─ 成功 → posts.status = 'posted', post_analytics 初期レコード生成
              └─ 失敗 → posts.retry_count + 1, 3回超過で status = 'failed', 管理者通知
```

#### 垢 BAN 回避ロジック

```
[タスク実行時の安全制御]

1. レート制限遵守
   - Twikit のエラーレスポンス（429 / RateLimitError）を検知
   - 自動バックオフ：15 分待機後に再試行

2. ランダム遅延挿入
   - いいね間隔: min_interval ～ max_interval 秒 (ガウス分布)
   - 例: 設定 30～90 秒 → random.gauss(60, 15) 秒

3. 1 日あたり上限
   - いいね: ≤ 500 / day（デフォルト上限 200）
   - フォロー: ≤ 400 / day（デフォルト上限 100）

4. 時間帯制限
   - 深夜帯（01:00-06:00 JST）は自動タスクを停止（設定可）

5. Twikit セッション管理
   - cookies.json をユーザーごとに暗号化保存
   - セッション切れ時は自動再ログイン（クレデンシャルは AES-256 で保管）

6. 操作パターンの人間的再現
   - 連続実行せず一定間隔でバースト→休止を繰り返す
   - 例: 10 アクション→5 分休止→10 アクション
```

## 3. 非機能要件

### 3.1 セキュリティ

| 項目 | 要件 |
|------|------|
| 通信暗号化 | 全通信 HTTPS（TLS 1.3）必須 |
| 認証 | JWT（RS256署名）、リフレッシュトークンはHTTP-Only Cookie |
| パスワード | bcrypt（cost 12）でハッシュ化 |
| API クレデンシャル保護 | X アカウントのパスワード・cookies を AES-256-GCM で暗号化してDB保存 |
| CSRF 対策 | SameSite=Strict Cookie + CSRF トークン |
| XSS 対策 | フロントエンド入力値のサニタイズ、CSP ヘッダー設定 |
| SQLインジェクション対策 | ORM（SQLAlchemy）のパラメータバインディングを使用 |
| レート制限 | API エンドポイントに IP ベースのレートリミット（slowapi） |
| シークレット管理 | 環境変数 / AWS Secrets Manager で管理、コードに直書き禁止 |
| 監査ログ | 認証イベント・設定変更を audit_logs テーブルに記録 |

### 3.2 パフォーマンス

| 指標 | 目標値 |
|------|--------|
| API レスポンスタイム（P95） | < 200 ms |
| ダッシュボード初期表示 | < 2 秒 |
| 投稿スケジューラー精度 | ± 60 秒以内 |
| 同時接続ユーザー数 | 1,000 ユーザー |
| DB クエリ最適化 | N+1 問題の排除、適切なインデックス設計 |
| キャッシュ | Redis を用いたダッシュボード集計値キャッシュ（TTL 5 分） |

### 3.3 可用性・信頼性

| 項目 | 要件 |
|------|------|
| 稼働率 | 99.5% 以上（月次） |
| バックアップ | PostgreSQL の日次スナップショット（30 日保持） |
| 障害通知 | Celery タスク失敗時のメール通知（管理者・ユーザー） |
| ヘルスチェック | `/healthz` エンドポイントで外形監視対応 |

### 3.4 拡張性

| 項目 | 要件 |
|------|------|
| マルチアカウント | 1 ユーザーが複数の X アカウントを管理可能 |
| マルチテナント | テナント（ユーザー）間のデータ完全分離 |
| 水平スケール | Celery Worker のスケールアウトに対応（Kubernetes / ECS） |
| 将来対応 SNS | Instagram・Threads 対応を視野に入れた抽象化設計 |
| API バージョニング | `/api/v1/` プレフィックスによるバージョン管理 |

### 3.5 運用・保守

| 項目 | 要件 |
|------|------|
| ログ | 構造化ログ（JSON）、ログレベル管理 |
| 監視 | Prometheus + Grafana / Datadog |
| デプロイ | CI/CD パイプライン（GitHub Actions） |
| 環境 | 開発（dev）/ ステージング（stg）/ 本番（prd）の 3 環境 |

## 5. 制約事項

1. X 規約遵守：Twikit は非公式クライアントであり、X 利用規約に反する操作（スパム・なりすまし等）は実装しない
2. 自動化の透明性：ユーザーは BAN リスクを理解した上でサービスを利用（利用規約で明示）
3. データ保持：退会後 30 日間はデータ保持、以降自動削除
4. 対象ブラウザ：Chrome 120+・Edge 120+（IE 非対応）
